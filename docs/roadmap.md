# Roadmap

Wishlist from the first day of real use (2026-09-20), in the order I'd build it. Nothing here is started.

## 1. Outputs that follow you (built 2026-09-20, headset-off switch untested on hardware)

One feature, three symptoms:

- **No virtual-device picker.** freeseries only works with its own virtual endpoint, so find the FxSound device by name and hide that choice. Keep the picker as a fallback when no such device exists (VB-Cable users).
- **Per-device correction.** Each output remembers its own headphone correction. (Until 2026-09-20 it also held the sound preset; see "Where the sound lives" below.)
- **Auto-switch.** A priority list of outputs. Headset turns off -> audio moves to the monitor and its EQ; headset comes back -> audio moves back. The engine already notices a dead output (`Status::Reconnecting`); today it retries the same device forever instead of falling to the next one.

This is also the robustness story: a missing headset must never mean silent audio.

## 2. Setup wizard (built 2026-09-20, real install path untested)

`app/src-tauri/resources/setup.ps1` installs the vendored, Microsoft-signed fxvad package (one UAC prompt) and names the endpoint "freeseries". The app opens the wizard by itself when no virtual device exists, watches for the device becoming the Windows default, then hands over to Devices. Verified: the script on Windows PowerShell 5.1 (dry run and rename), the elevation command line (unit test), the whole flow against the preview's simulated fresh PC. **Not verified:** the elevated install from inside the app, because the only test machine already has the driver.

Found on the way: renaming an endpoint (`PKEY_Device_DeviceDesc`) needs **no** admin rights, so it never prompts. The "(FxSound Audio Enhancer)" suffix is the driver's interface name and stays.

Still open: a one-click "make it default" (needs the undocumented `IPolicyConfig` COM interface that EarTrumpet and SoundSwitch use; today the wizard deep-links to Sound settings and detects the result), and uninstall.

## 3. Editor and UI pass (first pass done 2026-09-20)

Done since: a live spectrum analyser behind the curve (`src/spectrum.rs`: a tap on the processed audio, an own radix-2 FFT run off the audio thread, 96 log bands; drawn on a canvas outside React). Its display range (-84 to -12 dBFS after a 4.5 dB/octave tilt) was tuned against synthetic data only and wants a look with real music.

The EQ editor needs love and the app reads as an open-source project. Do it as a proper design pass with the `impeccable` skill, not piecemeal.

## Done 2026-09-20 (second batch)

- **Where the sound lives (changed 2026-09-20).** A sound preset belongs to a channel, a headphone correction to an output, and nothing else carries an EQ. Before, the output held a sound preset too and the Mixer let a channel name a second one: both ran in series, so a user with "PSense Game" on the channel and "PSense Media" on the output got two curves and two preamps, 10.6 dB down (found when the user reported low volume; every Windows endpoint volume measured 100% with `examples/volumes.rs`). Now the Equalizer and the Presets page work on one channel, picked with a Game / Chat / Media switch in the toolbar; the Mixer strip's picker sets the same curve and its thumbnail opens the editor on that channel. The engine is unchanged: channel presets travel in the plan (a plan with the same devices retunes the running session), the output preset is the correction alone. Saved settings migrate (`store.ts`, checked by `npm run check`): a channel's own pick wins, otherwise the main channel inherits what the first output played. The editor still draws the active output's correction as a dashed reference line, and headroom is worked out over correction plus sound. The analyser shows the whole mix, not the channel being edited. **Checked in the browser preview only.**
- **Starter sound presets** written for freeseries: Footsteps, Bass boost, Voice clarity, Late night, each with a preamp that cancels its loudest point.
- **Import / export** in Equalizer APO `ParametricEQ.txt` text: import from a file, copy the current sound to the clipboard.
- **Soft limiter** after the EQ (`eq::limit`): identity below -1 dBFS, bends towards full scale above it, no look-ahead so no latency.
- **Global hotkeys**: Ctrl+Shift+F9 / F10 previous / next sound preset, Ctrl+Shift+F11 bypass. Not Ctrl+Alt (that is AltGr on European layouts). A shortcut another app already owns is reported in Settings instead of failing the launch. **Untested in the real app**: the Rust side compiles, nothing has pressed the keys yet.

- **Agent access (built 2026-09-20).** An AI agent can tune the EQ with the user: an MCP endpoint (Streamable HTTP with plain JSON responses, spec 2025-11-25, no event stream) on 127.0.0.1:47630 (47631 in a dev build), off until switched on in Settings, which also hands out the `claude mcp add` command. `app/src-tauri/src/agent.rs` is only the HTTP edge, on std alone: loopback bind, a bearer token, foreign `Origin` or `Host` refused (a web page can reach 127.0.0.1; the MCP spec asks for exactly this), POST only. Every JSON-RPC message goes to the webview as an "agent-request" event and the answer comes back through `agent_reply`, because the state lives in the UI: the tools (`app/src/agent.ts`: get_state, listen, set_eq, use_preset, save_preset, search_headphones, use_headphone_correction) change it through the same setters as a click. set_eq validates and clamps like the editor, and without a preamp picks the one that puts the loudest point at 0 dB. A hand-tuned, unsaved curve is filed as "<name> (before agent)" before an agent replaces it. Setup, routing and anything elevated are out of an agent's reach. Checked: the HTTP edge by a Rust test, the protocol and set_eq by `npm run check`, all tools against the whole app in the browser preview. **Run end to end 2026-09-21** with curl against the dev build: handshake, tool list and get_state come back with the user's real channels, 401 without the token, 403 with a web origin. Still unproven: `listen` while the window sits in the tray, where WebView2 slows timers to about one a second.

- **Upgrading without uninstalling (2026-09-21).** The installer never needed the old version removed: over an existing install it shows a page whose second option is "Do not uninstall", and it has the update mode Tauri's own updater uses. `npm run upgrade` (`app/scripts/upgrade.ps1`) builds and runs it with `/P /UPDATE /NS /R`: no pages, settings and shortcuts stay, the app restarts. Flags read out of the generated `installer.nsi`; **the script has not been run**. It closes every `freeseries-app.exe`, a dev build included. Version 0.3.0 from here on, so an upgrade is an upgrade and not a same-version reinstall. An in-app updater (`tauri-plugin-updater`) is the next step and waits on two things that are the owner's: a public place for releases (there is no git remote yet) and a signing key only they hold.

- **Headset modules (2026-09-21).** Per-headset hardware support is a table, one file per headset, community-maintained except the Arctis Nova Pro Wireless (the only one we own). Replaces `arctis.rs`. The ChatMix dial drives the Game / Media balance; battery and mic mute show on the output strip. Details, the protocol and how to add a headset: `docs/headsets.md`. Microphone processing research and the route to try first (VB-CABLE as the virtual mic, our own capture APO as the fallback): `docs/mic.md`. Later, on the same kind of seam: clip capture with one track per channel (the engine already has every channel separately).

Still to do from the same list: switch the sound preset when a game launches (needs foreground-process watching and a rules UI), the `IAudioClient3` backend, README / updater / code signing for a public release.

## 5. Game / Media / Chat channels, mic EQ

Measured 2026-09-20 with `examples/process_probe.rs` (child process plays tones, parent captures its process-tree loopback and the endpoint loopback at once):

- Windows' per-process loopback returns the app's **raw stream**: a stereo tone comes back bit-for-level (-20.0 dBFS, L only); of a 7.1 stream it returns the front pair only (back-left: silence). It is pre-mix and pre-spatial, so it can never carry the Atmos/DTS render.
- It is taken **after** the session volume: muting the app in the mixer silences the endpoint loopback *and* the per-process capture. So "mute it on the endpoint, capture it per process" doesn't work, and neither does subtracting captures from the mix (the spatial renderer doesn't pass stereo bit-exactly).

What that leaves, best first:

1. **A second instance of the same signed driver. VERIFIED 2026-09-20.** `setup.ps1 -AddInstance` (elevated) created `ROOT\MEDIA\0002` from the package already installed: status OK, its own endpoint, and `examples/probe.rs` shows the two loopbacks are fully independent (a tone played into one reads -20.0 dBFS on its own loopback and digital silence on the other, both ways). Endpoints are named per instance without admin rights: "freeseries", "freeseries Media", then "freeseries Chat" (Media came second from 2026-09-21: music next to a game matters to more people than voice chat does; the balance slider sits between the main channel and whichever is second). From the same day the name people read is spelled "FreeSeries": the endpoints ("FreeSeries", "FreeSeries Media", "FreeSeries Chat"), the product name and the UI copy; crate, exe, paths, the logon task and the MCP server key stay lowercase. `setup.ps1` renames an endpoint that carries one of our names in the old spelling, so an upgrade fixes itself (run on the user's PC: both endpoints renamed, a second run changes nothing, the live engine never noticed). The main endpoint stays plain "FreeSeries" rather than "FreeSeries Game": most people never add a channel, and it is the one to make the default. The extra endpoints can't be hidden from Windows: a disabled endpoint can't be played into, and that is how an app gets onto a channel. The Devices page says so instead, and shows whether FreeSeries is the Windows default. This is Sonar's own model with no new driver to sign.

   **Built 2026-09-20.** The engine captures every channel's device in one session, applies that channel's EQ and volume, sums them and runs the output's EQ and the limiter over the mix (`src/wasapi.rs`). Hardware check through the CLI (`freeseries run 0,1 2`): a tone into either device arrives at the output at -19.9 dBFS, a 24 s soak shows 0 dropouts and 0 phase jumps, latency 13-31 ms per run. The app has a Mixer page (Game/Chat balance, per-channel volume, mute and EQ) and an "Add the chat device" action that runs `setup.ps1 -AddInstance` behind one UAC prompt. **Untested in the real app**, and that action has only ever been run by hand.

   **Apps into channels, built 2026-09-20.** `src/routing.rs` drives the per-app output device of the Windows volume mixer through the undocumented `Windows.Media.Internal.AudioPolicyConfig` (layout and IIDs from EarTrumpet; same vtable on Windows 11 and on Windows 10 before 21H2, different IID). Measured with a test process: pinned to "freeseries Chat" its tone reads -20.0 dBFS there and silence on the main device, the pin survives a relaunch (Windows stores it per app), un-pinning sends it back to the default. Two limits found: an app can only be pinned once it has an audio session (`E_INVALIDARG` before that), and an app moves when it next opens a stream (real apps reopen at once; a stream that ignores the invalidation stays put). The Mixer page has a board: a lane per channel, drag an app across, all processes of the same executable move together, with a per-app select as the keyboard route.

   **Quitting hands apps back (2026-09-21).** Windows keeps an app pinned to a channel's device whether FreeSeries runs or not, so after Quit those apps stayed silent even once the user pointed Windows back at their headphones; the way out was to reopen, drag everything off Media and quit again. Now the tray's Quit un-pins every app that sits on one of our virtual devices (`routing::release`, tested with a fake; a user's own pin to a real device is left alone), and the UI remembers which channel an app belongs on (`assignments` in the saved settings, by app name) and pins it again whenever audio is running: at the next start, and for apps that open later (checked every 5 s; pins found from before this existed are taken over once). Checked in the browser preview and by the Rust test; **the real quit has not been run**. **The Windows default follows the engine (2026-09-21):** see "Handing the default back" below. Limits: only apps that are running at Quit can be released (Windows offers no way to list pins of apps that aren't), a crash or a kill releases nothing.

   **Console, built 2026-09-20.** The Mixer page is a mixing console: one strip per channel (EQ thumbnail and picker, its apps, fader, mute, name plate), an output strip, and a Game/Chat crossfader. The whole strip is the drop target. Live peak meters come from the engine (`Dsp::levels()`, per channel after EQ and volume, plus "out" for the mix after the limiter), polled 20 times a second and painted outside React. Apps show their real icon (`routing::icon_of`, `SHGetFileInfoW` to RGBA; checked by eye against Spotify, Discord and Chrome with `examples/icon_dump.rs`). **Checked in the browser preview only**: a real mouse drag, the meters and the icons have not been seen inside the Tauri window.

2. **Mixer-only channels** as the fallback: group apps into Game/Chat/Media and drive their Windows session volumes (`ISimpleAudioVolume`, what the Volume Mixer does). Works with Atmos/DTS and adds no latency, but no per-channel EQ.

Mic processing (noise suppression, mic EQ) needs a virtual *capture* device; fxvad's capture pin is disabled in its signed INF. Parked.

## Handing the default back (2026-09-21)

The one failure every voice of the council named: the engine goes away and the PC is silent, because Windows still plays into our virtual device. Now the Windows default follows the engine. While it plays, the default is ours; when it stops, quits, crashes or is killed, every role (Console, Multimedia, Communications) that pointed at one of our devices moves to the output the engine was playing on, and the roles we moved come back when the engine runs again, unless the user has pointed them elsewhere in the meantime.

- `src/default_output.rs`: reading the default is documented API; setting it is `IPolicyConfig::SetDefaultEndpoint` (undocumented, what the Sound control panel uses; GUIDs and vtable slot 13 from EarTrumpet's source). `hand_back` / `take_back` decide first and move second, because Windows 11 drags Multimedia along when Console moves (seen on hardware, pinned in the test).
- `app/src-tauri/src/handback.rs`: the policy with its state in `handback.json` (app data) behind a `Store` trait. A watcher thread follows `Engine::status()`; Quit hands back on its way out; and for a death without a say, the app starts a second copy of its own exe as `--watchdog <pid> <state file>`, which waits for the app's process to end and then hands back. It shares nothing with the app but the file.
- A development build does none of this: the default belongs to the installed app running next to it.
- Checked on this PC: the setter (FreeSeries -> headphones -> FreeSeries, all three roles, `cargo run -- default [device#]`), and the real watchdog process against a stand-in that was killed: the default moved to the headphones within the 5 s I waited, the watchdog exited, the state file recorded it. **Not yet run: the installed app doing it by itself** (Stop, Quit, End task, and the take-back at the next start); that needs the next install.
- The installer closes every `freeseries-app.exe` by name, which includes the watchdog (good: it would otherwise hold the exe open), so an upgrade does not hand back; the app restarts right after.

## Latency (measured 2026-09-20 with `examples/latency.rs`)

The tool plays quiet noise into the virtual device, records the loopback of that device and of the output, and cross-correlates them on WASAPI's own capture timestamps. Self-against-self reads 0.0 ms.

- 0.1.1 as installed, FxSound -> Arctis: **64 ms**. Most of that was backlog: audio that queued up while the streams started (capture runs first) and was never given back. It varied from start to start.
- With the queue trimming in `src/wasapi.rs` (drop whatever is always left over, keep an 8 ms cushion), FxSound -> monitor: **25-27 ms**, the same on every start. Not yet measured on the Arctis route.
- Asking cpal for one-period buffers changed nothing. ~25 ms is the floor of shared-mode WASAPI at its 10 ms period: one period to capture, one to render, plus the cushion.

Measured again 2026-09-21 on the real route, installed app, three runs each within 0.2 ms: main channel -> Arctis Nova Pro Wireless **30 ms**, Media channel -> Arctis **51 ms**. A dev engine of the current code to the monitor reads 20 ms (main) and 21 ms (Media), so the 20 ms the Media channel loses on the installed build is unexplained: re-measure after the next install before chasing it.

**What the "glitch" lines in the log really were (2026-09-21, second and final reading).**

Two readings of the same log lines were wrong before this one, and both are kept here as a warning. First "a glitch every three minutes from clock drift" (the intervals run from 12 s to 35 min). Then "the tray app's capture thread is starved by builds, 5 runs of 5": every one of those five "witness" results was the test tone of `tools/glitch-under-load.ps1` itself starting and stopping on the installed app's Media channel. The user's run against the new build showed it: one "media capture glitch" in the second the tone began.

The group "2x capture glitch, dropped 4 ms" then, a while later, "playback ran dry N times" is **a sound starting and a sound stopping** on a channel, nothing else. Loopback delivers nothing while an endpoint is silent; when a sound starts, WASAPI flags the first packets as discontinuities (logged as glitches), they arrive as a burst (extra delay), and when the sound ends the queue empties while the channel still counts as talking (logged as running dry). Two of those three were only noise in the log. One was real: about a second after **every** sound that starts from silence, the old code cut the burst's 4 ms out of the middle of it.

Fixed in `src/wasapi.rs` (`Feed::mix_into`, pulled out of the playback closure so it can be tested with a ramp signal and a fake clock):
- A channel waking from silence holds its first samples until twice the cushion is queued, so the sound starts without holes and nothing of it is lost.
- Built-up delay is never cut out any more. It is **eased out**: the channel plays 0.5 % fast (2 % for more than 10 ms of backlog), interpolating between samples, until the measured excess is gone, and lands exactly on a sample again so that normal playback stays a bit-exact copy. Test: `a_sound_that_starts_from_silence_is_never_cut` (red before: samples missing a second in).
- ~~A real capture stall costs one gap: the audio that arrives late is dropped where the silence already is.~~ **Reverted 2026-09-22.** On the Arctis route this ran in a loop: a late packet ran playback dry, the "late" audio was cut, the queue was back below what the jitter needed, the next packet ran dry again. Measured on the installed app with a 30 s tone: 502 cuts, 31 dry seconds, 1343 phase jumps; the user heard it as crackling all evening. The queue now deepens to whatever the jitter needs (that is what the once-a-second easing measures against) and nothing is ever cut; a stall is one gap. Tests: `jitter_is_absorbed_by_a_deeper_queue_never_by_cutting`, `a_capture_stall_is_one_gap_and_the_delay_eases_out`.
- Discontinuities while a channel wakes are not reported; running dry is only reported for a channel that is still talking when the second is over.
- Audio threads join the Windows "Pro Audio" class (`AvSetMmThreadCharacteristicsW`, no dependency). Measured in the installed app: its two audio threads at priority 24, everything else at 8 to 10. Standard practice; no glitch on this PC has been shown to need it.

Measured on hardware (dev engine, Media -> monitor, tone started and stopped three times): the log shows only "easing out N ms", and `examples/soak.rs` reads 0 level dropouts and 0 phase jumps. That tool was blind before: it played 1 kHz, and a cut of whole milliseconds is whole cycles of 1 kHz. It now plays 1130 Hz and flags a change in how fast the phase moves, so a steady slide (drift, easing) passes and a cut does not. It still skips the first second of a run, which is where the old build's 4 ms cut fell, so the old cut was shown by the log and the unit test, not by this tool.

**Verified in the installed app (build of 19:46, 2026-09-21):** three audio threads at priority 24; the user's run of `tools/glitch-under-load.ps1` (60 s of tone under a from-scratch build) left nothing in the log but "easing out 17 ms" and "7 ms" where the tone began: no glitch, no dry, no cut.

**Open: about 19 ms that belong to one channel and are not in our queue.** Installed build, settled 6 s before measuring, repeatable to 0.3 ms: Game -> Arctis 48 ms, Media -> Arctis 29 ms. In the morning's build it was the other way round (30 and 51). The engine reports no excess for either channel, so the time is spent outside `Feed`: not in cpal's capture loop (it drains every packet on each wake), and cpal's capture timestamps are no help (callback and capture time read identical). A dev engine on both channels -> monitor read 37 and 32 ms today against 20 and 21 in the morning, so there is session-to-session variation of the same size too. Likely in how much audio sits in the WASAPI endpoint buffers, which cpal gives no control over (it fills whatever render space is available). This is an argument for the backend below rather than something to chase through cpal.

**Low-latency spike, 2026-09-22 (`examples/lowlat.rs`).** Two findings.
1. `IAudioClient3` buys nothing here: every endpoint on this PC (fxvad, NVIDIA HDMI, Realtek, the Arctis over USB) reports min = default = max = 10 ms. The drivers don't offer smaller engine periods, and `InitializeSharedAudioStream` refuses the loopback flag anyway (`AUDCLNT_E_INVALID_STREAM_FLAG`), so loopback capture stays on the plain initialise.
2. **The 10 ms period is not where the latency is.** A bare passthrough on raw WASAPI (loopback capture, event-driven render, one thread, a queue capped at two periods, no EQ) measured **7.2 to 8.0 ms** added latency Media -> monitor, where the cpal engine reads 20 to 37 ms on the same route (and 29 / 48 ms to the Arctis). 25 s of tone through it: 0 dropouts, 0 phase jumps, 0 dropped frames, 0 dry frames once audio was flowing. The 12 to 40 ms the current engine spends are in how cpal fills the render buffer (whatever is free, and the 22 ms WASAPI buffer is mostly free) and in queues between its two threads.

So the backend is worth building and is simpler than planned: own WASAPI, no IAudioClient3, one render-event-paced thread per session that drains every channel's loopback and mixes straight into the render buffer, with `Feed`'s priming and easing kept (the spike had none and got away with it only because its cap of two periods just drops the excess). Target on the evidence: ~8 ms plus the cushion, the same on every channel, since one thread reads all channels at the same moment. Both endpoints must share the mix format (the spike requires it; the engine's ponytail note about resampling stands).

**Native backend, built 2026-09-22 (`src/native.rs`).** WASAPI direct, one thread per session woken by the render event: drains every channel's loopback, channel EQ and volume, mix, output EQ, limiter, render buffer. Same `Feed` (priming, easing) as the cpal backend, which stays in the tree (`FREESERIES_CPAL=1` in the CLI runs it); the app uses the native one. 19 engine tests unchanged. Measured, both channels -> monitor, settled: **main 9.4 ms** (cpal read 20-37 on this route), 25 s tone 0 dropouts 0 phase jumps, 0 dry. Wake jitter up to 3.4 ms against a 12 ms margin.

Two things found on the way, both outside the backend:
- The Media channel reads ~16-20 ms more than the main one on every backend, including the raw spike with no queue at all (device 0 -> monitor 1-11 ms, device 1 -> monitor 24 ms), while both channels hold the same 7-8 ms leftover in their queues. So it is the second fxvad instance's loopback (or its position stamps that `latency.rs` relies on), not the engine. Unverified beyond that; a microphone measurement would settle whether it is real delay or a stamp offset.
- Running `latency.rs` right before `soak.rs` leaves the virtual device's loopback slipping for a while: the tone tool alone, with no engine in the path, then shows phase jumps (4, 6, 17 in three runs; 0 in five runs without the preamble). Two afternoons of "the engine glitches" readings had that preamble. Proven by dumping the engine's input and output: the jumps were already in the input. Noted at the top of both tools.

**Not yet run on the Arctis or in the installed app.**

**Next step for latency:** our own WASAPI backend on `IAudioClient3`, which lets shared-mode streams run at the driver's minimum period (often ~3 ms) instead of 10 ms. `AudioBackend` is already the seam for it. Target: ~10 ms. Whether fxvad and the user's outputs support small periods is unverified.

## Observed, not yet acted on

- **Glitches under heavy CPU load.** The installed app logged three capture glitches at 12:59 on 2026-09-20 while a Rust build was saturating the CPU, and none in the quiet 75 minutes before. The capture and playback callbacks share a mutex'd queue and run at whatever priority cpal gives them. If this shows up while gaming, the fix is the lock-free ring buffer already flagged in `src/wasapi.rs`, plus checking the audio threads register with MMCSS ("Pro Audio").
